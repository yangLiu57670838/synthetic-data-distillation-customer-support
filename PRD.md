# Product Requirements Document

## Synthetic-Data Distillation for Customer-Support Language Models

**Status:** Draft 1.0  
**Project type:** Research and AI engineering portfolio project  
**Owner:** Yang Liu  

## 1. Executive summary

This project investigates whether high-quality synthetic customer-support data generated by a capable teacher language model can improve a smaller, inexpensive student model.

The system will use a curated customer-support dataset as the source of domain taxonomy and seed examples. A teacher model will expand selected seeds into diverse instruction-response examples. Automated checks, model-based review, and limited human review will filter the generated data. A small open-weight model will then be fine-tuned using QLoRA and evaluated against controlled baselines.

The final deliverables will include a reproducible data-generation pipeline, versioned datasets, fine-tuned model, evaluation suite, experiment report, inference service, and public demonstration.

## 2. Problem statement

Small language models are cheaper and easier to deploy than frontier models, but they may perform poorly on specialized customer-support tasks. Human-labelled training data is expensive, slow to produce, and often unavailable.

Frontier models can generate large quantities of synthetic training data, but synthetic data may contain incorrect labels, duplicated patterns, unrealistic language, unsafe responses, and teacher-specific biases. It is therefore insufficient to demonstrate that synthetic data can be generated; the project must measure when it helps, how it should be filtered, and whether improvements generalize to independent test examples.

## 3. Research question

> Does filtered synthetic instruction data generated by a capable teacher model improve the quality of a small customer-support language model compared with using the original curated dataset alone?

### 3.1 Secondary questions

1. Does filtered synthetic data outperform unfiltered synthetic data?
2. Does combining original and synthetic data outperform either source alone?
3. Which synthetic-data characteristics—volume, diversity, difficulty, or filtering—contribute most to improvement?
4. What are the cost, latency, and quality trade-offs between teacher models and student models?
5. Does synthetic training improve rare, ambiguous, noisy, multi-intent, and out-of-scope requests?

## 4. Hypotheses

- **H1:** Fine-tuning on original plus filtered synthetic data will outperform fine-tuning on original data alone.
- **H2:** Filtering will improve performance relative to using the same quantity of unfiltered synthetic data.
- **H3:** Synthetic data will provide the largest gains on rare intents and linguistically diverse inputs.
- **H4:** Increasing synthetic-data volume without adequate diversity or filtering will produce diminishing or negative returns.
- **H5:** A fine-tuned small model will deliver lower inference cost and latency than the teacher while retaining useful domain performance.

## 5. Goals

### 5.1 Product goals

- Build an end-to-end, reproducible synthetic-data and fine-tuning pipeline.
- Produce a deployable customer-support model that identifies intent and generates an appropriate response.
- Provide traceable links between source seeds, generation prompts, synthetic examples, filtering decisions, training runs, and evaluation results.
- Publish artifacts that demonstrate both research rigor and production engineering skills.

### 5.2 Research goals

- Establish strong non-fine-tuned and original-data baselines.
- Run controlled experiments in which only one major variable changes at a time.
- Evaluate on an independent test set not generated by the training-data teacher.
- Report uncertainty, failure cases, limitations, and negative results.

### 5.3 Non-goals

- Building a production customer-service platform with CRM integrations.
- Replacing human support agents in high-risk scenarios.
- Training a foundation model from scratch.
- Claiming general customer-support capability from one dataset or domain.
- Evaluating hidden model reasoning or chain-of-thought.

## 6. Users and stakeholders

### 6.1 Primary users

- Researchers examining synthetic-data quality and knowledge distillation.

### 6.2 Demonstration user

A user submits a customer-support request and receives:

- Predicted intent and confidence where supported.
- A concise response following the defined support policy.
- An escalation or clarification request when the problem is ambiguous, unsafe, or outside scope.

## 7. Use cases

The model should handle:

- Refund and return requests.
- Delivery status and delivery-delay questions.
- Account access problems.
- Payment and billing issues.
- Product or service complaints.
- Subscription cancellation.
- Missing information that requires clarification.
- Multiple intents in one message.
- Misspellings, informal language, and varied tone.
- Out-of-scope, unsafe, or adversarial requests.

## 8. Data strategy

### 8.1 Seed dataset

The initial seed source will be the [Bitext Gen AI Chatbot Customer Support Dataset on Kaggle](https://www.kaggle.com/datasets/bitext/bitext-gen-ai-chatbot-customer-support-dataset). It provides customer-support categories, 27 intent labels, instruction-response pairs, entity/slot information, and linguistic variation.

#### Why the Kaggle dataset is needed

The Kaggle dataset supplies the **domain structure and supervision** for the project. In particular, it provides:

- A predefined intent taxonomy rather than allowing the teacher model to invent inconsistent or overlapping labels.
- Seed customer messages that demonstrate what each intent means.
- Example support responses that help define the target task and response style.
- A reproducible baseline dataset against which synthetic-data augmentation can be compared.
- Class labels required for intent-classification metrics such as macro-F1 and per-intent recall.

The teacher model does not replace this structure. Its role is to expand selected seeds into more diverse, difficult, and policy-controlled examples. For example, a seed labelled `refund_request` can be expanded into formal, informal, misspelled, ambiguous, angry, or incomplete refund requests while retaining the same intended label.

The Kaggle dataset will therefore be used for three distinct purposes:

1. **Taxonomy source:** define the permitted categories and intents.
2. **Seed source:** ground teacher-model generation in representative examples.
3. **Baseline training source:** measure ordinary fine-tuning before synthetic data is added.

It will not be treated as an independent real-world test set, because its examples were produced using a hybrid synthetic-generation and linguistic-curation methodology.

#### Why the Hugging Face synthetic-data workflow is needed

The project will follow and adapt the [Hugging Face Synthetic Data Generator workflow](https://huggingface.co/blog/synthetic-data-generator). This resource is not a replacement dataset. It is a reference implementation and workflow for turning a task description, seed examples, and a teacher LLM into structured synthetic classification or conversational data.

It is needed because it provides a practical pattern for:

- Prompting a teacher model to generate structured examples.
- Producing data suitable for supervised fine-tuning.
- Reviewing and curating generated examples before training.
- Exporting versioned datasets to the Hugging Face Hub.
- Connecting synthetic-data creation to the later model-training workflow.

The project will implement its own scripted, version-controlled pipeline rather than relying only on a no-code interface. The Hugging Face workflow will guide the design, while project-specific schemas, quality filters, provenance tracking, and evaluation controls will ensure research reproducibility.

Together, the resources form this pipeline:

```text
Kaggle Bitext dataset
  → intent taxonomy and seed examples
  → teacher-model synthetic generation
  → Hugging Face-style validation and curation workflow
  → versioned training dataset
  → student-model fine-tuning and evaluation
```

The project must record:

- Dataset version and retrieval date.
- Licence and redistribution conditions.
- Original schema and transformation steps.
- Known synthetic or curated provenance.
- Duplicate, class-balance, leakage, and quality analysis.

The Bitext dataset must be described as a curated dataset produced using hybrid generation and linguistic curation, not as purely natural customer conversations. Its licence, terms, and current data card must be reviewed before publishing modified or derived data.

### 8.2 Dataset partitions

Data must be partitioned before synthetic generation:

- **Seed/training pool:** examples available for training and generation.
- **Validation set:** examples used for model selection and threshold tuning.
- **Independent test set:** human-written or independently sourced examples unavailable to the generation teacher.
- **Challenge set:** ambiguous, noisy, rare-intent, multi-intent, out-of-scope, safety, and prompt-injection cases.

Near-duplicate detection must be applied across all partitions to reduce leakage.

### 8.3 Synthetic-data schema

Each generated record should contain at least:

```json
{
  "example_id": "syn_000001",
  "parent_seed_ids": ["seed_0012"],
  "category": "ORDER",
  "intent": "refund_request",
  "user_message": "The item arrived broken. Can I get my money back?",
  "assistant_response": "I can help with a refund request...",
  "difficulty": "medium",
  "variation_type": ["paraphrase", "negative_tone"],
  "teacher_model": "configured-teacher-model",
  "generation_prompt_version": "v1",
  "generation_parameters": {},
  "automated_checks": {},
  "judge_scores": {},
  "human_review": null,
  "accepted": true
}
```

### 8.4 Synthetic variation types

Generation should cover:

- Semantic paraphrases.
- Formal and informal language.
- Spelling, grammar, and punctuation noise.
- Short, incomplete, and indirect requests.
- Neutral, frustrated, and angry tones.
- Rare terminology and regional language variation.
- Ambiguous and overlapping intents.
- Multiple intents in one message.
- Missing required information.
- Out-of-scope requests.
- Safety-sensitive and adversarial requests.

### 8.5 Data-quality controls

Required automated checks:

- JSON/schema validation.
- Required-field and allowed-label validation.
- Exact duplicate removal.
- Semantic near-duplicate detection.
- Language and character-set checks.
- Minimum and maximum length checks.
- Response-format and policy checks.
- Personally identifiable information detection.
- Toxicity and unsafe-content checks.
- Intent-label consistency scoring.
- Seed/test similarity and leakage checks.

Model-based review may score realism, label correctness, response quality, safety, and difficulty. A random stratified sample must also receive human review. The same teacher should not be the sole generator, judge, and final evaluator without independent validation.

## 9. Model strategy

### 9.1 Teacher model

A capable API model will generate synthetic examples and optionally review difficult cases. The exact model must be configured rather than hard-coded so that experiments can compare teacher quality and cost.

The teacher is needed to create useful variation that cannot be obtained by simply duplicating or mechanically paraphrasing the seed dataset. It will generate difficult cases, policy-compliant responses, noisy language, rare-intent examples, multi-intent requests, and out-of-scope cases. It may also review examples whose label or response quality cannot be decided reliably with deterministic rules.

The teacher will not be used as the deployed application model. It is an offline data-production component whose knowledge is distilled into the smaller student. This separation allows the project to study whether a one-time generation expense can reduce ongoing inference cost.

Recommended initial strategy:

- Use a balanced frontier model for most generation.
- Use deterministic code and inexpensive models for simple validation.
- Use the strongest model only for difficult generation, adjudication, and a small gold-quality subset.
- Use batch processing where available and appropriate.

### 9.2 Student model

The initial student will be [`Qwen/Qwen2.5-1.5B-Instruct`](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), fine-tuned with QLoRA. A later model-size experiment may use [`HuggingFaceTB/SmolLM3-3B`](https://huggingface.co/HuggingFaceTB/SmolLM3-3B) or another documented open-weight model.

The student is needed because the goal is not merely to call an expensive API model. The goal is to produce a smaller specialized model that can be controlled, fine-tuned, evaluated, versioned, and deployed at lower marginal cost and with fewer external dependencies. Comparing the base student with students trained on original, synthetic, and combined data is also the central scientific experiment.

Student-selection requirements:

- Clear licence permitting the intended use and artifact publication.
- Compatibility with Hugging Face Transformers, TRL, and PEFT.
- Feasible fine-tuning on accessible GPU infrastructure.
- Reproducible tokenizer and chat-template configuration.

## 10. Functional requirements

### FR-1: Data ingestion

The pipeline must download or accept a versioned seed dataset, validate its schema, normalize fields, and generate a data-quality report.

### FR-2: Synthetic generation

The pipeline must generate structured synthetic examples from selected seeds and taxonomy definitions. It must persist model name, prompt version, parameters, token usage, cost estimate, timestamps, and parent seed IDs.

### FR-3: Filtering

The pipeline must apply deterministic and model-based quality checks, preserve rejected examples for analysis, and record rejection reasons.

### FR-4: Dataset versioning

Each training dataset must have a manifest containing its source versions, row counts, class distribution, prompt versions, filters, checksums, and creation date.

### FR-5: Fine-tuning

The training system must support QLoRA/SFT, deterministic seeding where possible, resumable checkpoints, configurable hyperparameters, and experiment logging.

### FR-6: Evaluation

The evaluation suite must score every experimental condition on the same frozen test sets and produce aggregate, per-intent, per-difficulty, safety, latency, and cost results.

### FR-7: Inference service

The final student model must be accessible through a small API or interactive demo with structured input validation, error handling, and latency measurement.

### FR-8: Reproducibility

A new developer must be able to reproduce data processing, a small generation run, fine-tuning, and evaluation from documented commands and configuration files.

## 11. Experimental design

### 11.1 Required conditions

| ID | Condition | Purpose |
|---|---|---|
| A | Base student without fine-tuning | Establish zero-shot baseline |
| B | Student fine-tuned on original curated data | Establish ordinary SFT baseline |
| C | Student fine-tuned on unfiltered synthetic data | Measure raw synthetic-data value |
| D | Student fine-tuned on filtered synthetic data | Measure filtering value |
| E | Student fine-tuned on original plus filtered synthetic data | Test primary hypothesis |

### 11.2 Recommended ablations

- Synthetic-data volume: 1k, 5k, 10k, and 20k examples.
- Teacher tier: inexpensive versus balanced versus strongest teacher.
- Filtering: deterministic only, model judge only, and combined filtering.
- Data composition: balanced versus natural class distribution.
- Student size: approximately 1.5B versus 3B parameters.
- Difficult examples: included versus excluded.

### 11.3 Controls

- Use identical frozen evaluation sets across conditions.
- Hold training steps or observed training tokens constant where appropriate.
- Repeat important experiments with multiple random seeds.
- Record prompt, dependency, model, dataset, and hardware versions.
- Prevent test examples or close paraphrases from entering teacher prompts or training data.

## 12. Evaluation plan

### 12.1 Intent metrics

- Accuracy.
- Macro-F1 and weighted-F1.
- Per-intent precision, recall, and F1.
- Confusion matrix.
- Out-of-scope detection AUROC/F1 where applicable.
- Calibration error where confidence scores are available.

### 12.2 Response metrics

- Task correctness.
- Relevance and completeness.
- Policy compliance.
- Hallucination rate.
- Correct clarification or escalation behavior.
- Safety failure rate.
- Human preference or rubric scores.

Lexical-overlap metrics must not be treated as sufficient measures of response quality.

### 12.3 Operational metrics

- Median and p95 latency.
- Input and output tokens.
- Generation, training, and evaluation cost.
- Peak GPU memory.
- Training duration.
- Throughput.
- Model artifact size.

### 12.4 Statistical analysis

- Report sample counts and confidence intervals.
- Use bootstrap intervals or suitable paired tests for primary comparisons.
- Correct or clearly qualify multiple comparisons.
- Include effect sizes, not only p-values.
- Analyze failure categories and representative examples.

## 13. Success criteria

The project is successful when:

1. Condition E improves independent-test macro-F1 or the primary response-quality metric over Condition B by a predefined meaningful margin.
2. The improvement is accompanied by uncertainty estimates and does not depend only on teacher-generated evaluation data.
3. Filtered synthetic data performs better than or uses fewer examples than unfiltered synthetic data at similar quality.
4. The final student meets documented latency and resource targets on the selected deployment hardware.
5. All published artifacts contain adequate provenance, licence, limitation, and reproducibility documentation.
6. The project produces a defensible conclusion even if the primary hypothesis is not supported.

Initial target values, to be finalized after baseline measurement:

- At least 3 percentage points improvement in macro-F1 over original-data-only SFT, or a clearly justified equivalent improvement in response quality.
- Less than 2% critical safety or policy failures on the challenge set.
- At least 80% schema-valid synthetic generations before filtering.
- At least 90% agreement between accepted synthetic labels and a human-reviewed stratified sample.
- Reproduction of the main evaluation table from a documented command.

## 16. Responsible AI, privacy, and security

- Do not include real personal or confidential customer information.
- Detect and remove generated PII before training or publication.
- Document teacher-provider data-handling settings and retention policy.
- Respect source-dataset and model licences.
- Record synthetic-data provenance in the dataset card.
- Evaluate demographic, language, and tone-related performance disparities.
- Prevent the demo from claiming authority over refunds, payments, legal decisions, or account changes.
- Require escalation for sensitive, unsafe, or unsupported cases.
- Treat LLM-judge scores as fallible measurements and validate them against human review.

## 17. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Teacher generates incorrect labels | Student learns systematic errors | Label checks, independent judge, human sample review |
| Synthetic examples lack diversity | Apparent scale without generalization | Diversity prompts, embedding analysis, coverage reports |
| Train-test leakage | Inflated results | Pre-split data, semantic leakage checks, independent test creation |
| Same model family generates and evaluates | Biased evaluation | Independent evaluator, deterministic metrics, human review |
| Dataset licence is unclear or restrictive | Cannot publish artifacts | Licence audit and publish only permitted derivatives |
| API costs exceed budget | Incomplete experiments | Pilot runs, token caps, batching, caching, tiered teachers |
| Limited GPU availability | Training delays | QLoRA, small models, sampled experiments, checkpointing |
| Student memorizes canned responses | Poor real-world behavior | Challenge set, paraphrase testing, response diversity analysis |
| Results are negative | Perceived project failure | Pre-register hypotheses and present rigorous negative findings |

## 18. Milestones

### Phase 1: Baseline and data audit

- Create repository and reproducible environment.
- Ingest, profile, and document the seed dataset.
- Define task taxonomy and response policy.
- Freeze validation, independent test, and challenge sets.
- Evaluate the base student and original-data SFT baseline.

### Phase 2: Synthetic-data pilot

- Design versioned generation prompts and schemas.
- Generate a small pilot dataset.
- Measure schema validity, diversity, label consistency, and cost.
- Conduct initial human review and revise prompts.

### Phase 3: Generation and filtering

- Generate the main synthetic datasets.
- Apply validation, deduplication, quality scoring, and review.
- Publish data manifests and quality reports.

### Phase 4: Fine-tuning and experiments

- Train Conditions A–E.
- Run volume and filtering ablations.
- Track hardware, cost, hyperparameters, and random seeds.

### Phase 5: Evaluation and analysis

- Run frozen evaluations.
- Calculate uncertainty and effect sizes.
- Perform subgroup and error analysis.
- Write the technical report.

### Phase 6: Deployment and publication

- Quantize and serve the selected model.
- Build an interactive Hugging Face Space or equivalent demo.
- Publish model and dataset cards where licensing permits.
- Publish a polished Kaggle notebook and GitHub repository.

## 21. Definition of done

The project is complete when all required experimental conditions have been run, the frozen independent evaluation has been reported, the main results can be reproduced from documented configurations, and the repository contains sufficient data/model provenance, tests, cards, limitations, and deployment instructions for external review.
