# Product Requirements Document

## Synthetic-Data Distillation for Customer-Support Language Models

**Status:** Draft 1.1  
**Project type:** Research  
**Author:** Yang Liu  

**Study scope:** a cost-constrained preliminary study (see section 11.4). The full experimental matrix in section 11.2 is deferred.  

## 1. Executive summary

This project investigates whether high-quality synthetic customer-support data generated by a capable teacher language model can improve a smaller, inexpensive student model.

The system will use a curated customer-support dataset as the source of domain taxonomy and seed examples. A teacher model will expand selected seeds into diverse instruction-response examples. Automated checks, model-based review, and limited human review will filter the generated data. A small open-weight model will then be fine-tuned using QLoRA and evaluated against controlled baselines.

Intended outputs include a reproducible data-generation pipeline, versioned datasets, a fine-tuned student model, an evaluation suite, and a research report.

This revision limits the present study to a teacher-API pilot, approximately 1,000 main synthetic examples, and training conditions A, B, and E (D if compute budget remains). Volume, teacher-tier, and model-size ablations remain part of the full research design and are out of scope for the current budget.

## 2. Problem statement

Small language models are cheaper and easier to deploy than frontier models, but they may perform poorly on specialized customer-support tasks. Human-labelled training data is expensive, slow to produce, and often unavailable.

Frontier models can generate large quantities of synthetic training data, but synthetic data may contain incorrect labels, duplicated patterns, unrealistic language, unsafe responses, and teacher-specific biases. It is therefore insufficient to demonstrate that synthetic data can be generated; the project must measure when it helps, how it should be filtered, and whether improvements generalize to independent test examples.

## 3. Research question

> Does filtered synthetic instruction data generated by a capable teacher model improve the quality of a small customer-support language model compared with using the original curated dataset alone?

### 3.1 Secondary questions

1. Does filtered synthetic data outperform unfiltered synthetic data?
2. Does combining original and synthetic data outperform either source alone?
3. Which synthetic-data characteristics—volume, diversity, difficulty, or filtering—contribute most to improvement?
4. What are the cost, latency, and quality trade-offs between teacher models and student models?
5. Does synthetic training improve rare, ambiguous, noisy, multi-intent, and out-of-scope requests?

## 4. Hypotheses

- **H1:** Fine-tuning on original plus filtered synthetic data will outperform fine-tuning on original data alone.
- **H2:** Filtering will improve performance relative to using the same quantity of unfiltered synthetic data.
- **H3:** Synthetic data will provide the largest gains on rare intents and linguistically diverse inputs.
- **H4:** Increasing synthetic-data volume without adequate diversity or filtering will produce diminishing or negative returns.
- **H5:** A fine-tuned small model will deliver lower inference cost and latency than the teacher while retaining useful domain performance.

## 5. Goals

### 5.1 Product goals

- Build an end-to-end, reproducible synthetic-data and fine-tuning pipeline.
- Produce a deployable customer-support model that identifies intent and generates an appropriate response.
- Provide traceable links between source seeds, generation prompts, synthetic examples, filtering decisions, training runs, and evaluation results.
- Record provenance so experiments can be inspected and reproduced.

### 5.2 Research goals

- Establish strong non-fine-tuned and original-data baselines.
- Run controlled experiments in which only one major variable changes at a time.
- Evaluate on an independent test set not generated by the training-data teacher.
- Report uncertainty, failure cases, limitations, and negative results.

### 5.3 Non-goals

- Building a production customer-service platform with CRM integrations.
- Replacing human support agents in high-risk scenarios.
- Training a foundation model from scratch.
- Claiming general customer-support capability from one dataset or domain.
- Evaluating hidden model reasoning or chain-of-thought.

## 8. Data strategy

### 8.1 Seed dataset

The initial seed source will be the [Bitext Gen AI Chatbot Customer Support Dataset on Kaggle](https://www.kaggle.com/datasets/bitext/bitext-gen-ai-chatbot-customer-support-dataset). It provides customer-support categories, 27 intent labels, instruction-response pairs, entity/slot information, and linguistic variation.

#### Why the Kaggle dataset is needed

The Kaggle dataset supplies the **domain structure and supervision** for the project. In particular, it provides:

- A predefined intent taxonomy rather than allowing the teacher model to invent inconsistent or overlapping labels.
- Seed customer messages that demonstrate what each intent means.
- Example support responses that help define the target task and response style.
- A reproducible baseline dataset against which synthetic-data augmentation can be compared.
- Class labels required for intent-classification metrics such as macro-F1 and per-intent recall.

The teacher model does not replace this structure. Its role is to expand selected seeds into more diverse, difficult, and policy-controlled examples. For example, a seed labelled `refund_request` can be expanded into formal, informal, misspelled, ambiguous, angry, or incomplete refund requests while retaining the same intended label.

The Kaggle dataset will therefore be used for three distinct purposes:

1. **Taxonomy source:** define the permitted categories and intents.
2. **Seed source:** ground teacher-model generation in representative examples.
3. **Baseline training source:** measure ordinary fine-tuning before synthetic data is added.

It will not be treated as an independent real-world test set, because its examples were produced using a hybrid synthetic-generation and linguistic-curation methodology.

#### Why the Hugging Face synthetic-data workflow is needed

The project will follow and adapt the [Hugging Face Synthetic Data Generator workflow](https://huggingface.co/blog/synthetic-data-generator). This resource is not a replacement dataset. It is a reference implementation and workflow for turning a task description, seed examples, and a teacher LLM into structured synthetic classification or conversational data.

It is needed because it provides a practical pattern for:

- Prompting a teacher model to generate structured examples.
- Producing data suitable for supervised fine-tuning.
- Reviewing and curating generated examples before training.
- Exporting versioned datasets to the Hugging Face Hub.
- Connecting synthetic-data creation to the later model-training workflow.

The project will implement its own scripted, version-controlled pipeline rather than relying only on a no-code interface. The Hugging Face workflow will guide the design, while project-specific schemas, quality filters, provenance tracking, and evaluation controls will ensure research reproducibility.

Together, the resources form this pipeline:

```text
Kaggle Bitext dataset
  → intent taxonomy and seed examples
  → teacher-model synthetic generation
  → Hugging Face-style validation and curation workflow
  → versioned training dataset
  → student-model fine-tuning and evaluation
```

The project must record:

- Dataset version and retrieval date.
- Licence and redistribution conditions.
- Original schema and transformation steps.
- Known synthetic or curated provenance.
- Duplicate, class-balance, leakage, and quality analysis.

The Bitext dataset must be described as a curated dataset produced using hybrid generation and linguistic curation, not as purely natural customer conversations. Its licence, terms, and current data card must be reviewed before publishing modified or derived data.

### 8.2 Dataset partitions

Data must be partitioned before synthetic generation:

- **Seed/training pool:** examples available for training and generation.
- **Validation set:** examples used for model selection and threshold tuning.
- **Independent test set:** human-written or independently sourced examples unavailable to the generation teacher.
- **Challenge set:** ambiguous, noisy, rare-intent, multi-intent, out-of-scope, safety, and prompt-injection cases.

These challenge types are chosen because a high average score on ordinary Bitext-style examples can hide the failures that matter in support: unclear requests, messy language, uncommon intents, mixed goals, and cases that should be refused or escalated. They match hypothesis H3 and secondary question 5 (gains on rare, ambiguous, noisy, multi-intent, and out-of-scope inputs) and the use cases in section 7. The set is carved out before generation so the teacher and student training pool do not see it. Average metrics stay on the frozen test set; the challenge set is the stress test.

Near-duplicate detection must be applied across all partitions to reduce leakage.

### 8.3 Synthetic-data schema

Each generated record should contain at least:

```json
{
  "example_id": "syn_000001",
  "parent_seed_ids": ["seed_0012"],
  "category": "ORDER",
  "intent": "refund_request",
  "user_message": "The item arrived broken. Can I get my money back?",
  "assistant_response": "I can help with a refund request...",
  "difficulty": "medium",
  "variation_type": ["paraphrase", "negative_tone"],
  "teacher_model": "configured-teacher-model",
  "generation_prompt_version": "v1",
  "generation_parameters": {},
  "automated_checks": {},
  "judge_scores": {},
  "human_review": null,
  "accepted": true
}
```

### 8.4 Synthetic variation types

Generation should cover:

- Semantic paraphrases.
- Formal and informal language.
- Spelling, grammar, and punctuation noise.
- Short, incomplete, and indirect requests.
- Neutral, frustrated, and angry tones.
- Rare terminology and regional language variation.
- Ambiguous and overlapping intents.
- Multiple intents in one message.
- Missing required information.
- Out-of-scope requests.
- Safety-sensitive and adversarial requests.

### 8.5 Data-quality controls

Required automated checks:

- JSON/schema validation.
- Required-field and allowed-label validation.
- Exact duplicate removal.
- Semantic near-duplicate detection.
- Language and character-set checks.
- Minimum and maximum length checks.
- Response-format and policy checks.
- Personally identifiable information detection.
- Toxicity and unsafe-content checks.
- Intent-label consistency scoring.
- Seed/test similarity and leakage checks.

Model-based review may score realism, label correctness, response quality, safety, and difficulty. A random stratified sample must also receive human review. The same teacher should not be the sole generator, judge, and final evaluator without independent validation.

## 9. Model strategy

### 9.1 Teacher model

A capable API model will generate synthetic examples and optionally review difficult cases. The exact model must be configured rather than hard-coded so that experiments can compare teacher quality and cost.

The teacher is needed to create useful variation that cannot be obtained by simply duplicating or mechanically paraphrasing the seed dataset. It will generate difficult cases, policy-compliant responses, noisy language, rare-intent examples, multi-intent requests, and out-of-scope cases. It may also review examples whose label or response quality cannot be decided reliably with deterministic rules.

The teacher will not be used as the deployed application model. It is an offline data-production component whose knowledge is distilled into the smaller student. This separation allows the project to study whether a one-time generation expense can reduce ongoing inference cost.

Recommended initial strategy:

- Use a balanced frontier model for most generation.
- Use deterministic code and inexpensive models for simple validation.
- Use the strongest model only for difficult generation, adjudication, and a small gold-quality subset.
- Use batch processing where available and appropriate.

### 9.2 Student model

The initial student will be [`Qwen/Qwen2.5-1.5B-Instruct`](https://huggingface.co/Qwen/Qwen2.5-1.5B-Instruct), fine-tuned with QLoRA. A later model-size experiment may use [`HuggingFaceTB/SmolLM3-3B`](https://huggingface.co/HuggingFaceTB/SmolLM3-3B) or another documented open-weight model.

The student is needed because the goal is not merely to call an expensive API model. The goal is to produce a smaller specialized model that can be controlled, fine-tuned, evaluated, versioned, and deployed at lower marginal cost and with fewer external dependencies. Comparing the base student with students trained on original, synthetic, and combined data is also the central scientific experiment.

Student-selection requirements:

- Clear licence permitting the intended use and artifact publication.
- Compatibility with Hugging Face Transformers, TRL, and PEFT.
- Feasible fine-tuning on accessible GPU infrastructure.
- Reproducible tokenizer and chat-template configuration.

**Tokenizer requirement:** the student tokenizer (pin to a specific Hugging Face revision) must be used at every stage that involves token counting or sequence construction: length checks during filtering, sequence-length statistics in the quality report, chat-template formatting before training, and token-count measurement in the evaluation suite. Do not use a different tokenizer (e.g. the teacher model's tokenizer or a generic tiktoken) for any of these steps. The tokenizer revision and vocabulary size must be recorded in every dataset manifest and training config.

### 9.3 Fine-tuning method: QLoRA instead of full-parameter fine-tuning

**Why not full-parameter fine-tuning:**
Full-parameter fine-tuning updates all ~1.5 billion weights. This requires storing the model weights, the gradients, and the Adam optimizer states (two momentum tensors per parameter) simultaneously in GPU VRAM. For a 1.5B model in float16 this is approximately 24–48 GB of VRAM. Available GPU infrastructure (CUDA GPU via cloud notebook) typically has 16–40 GB, making full-parameter fine-tuning impractical or unstable at this scale. Full-parameter fine-tuning also risks catastrophic forgetting of the base model's general language capabilities.

**LoRA without quantization:**
Standard LoRA adds the same small trainable matrices (ΔW = A × B) but loads base model weights in their original float16 precision. For a 1.5B model the base weights alone occupy ~3 GB, but the Adam optimizer states and activations still push total VRAM to ~12–20 GB. Standard LoRA is feasible on a 16–24 GB GPU but leaves little headroom for larger batch sizes or longer sequences.

**Why QLoRA instead of LoRA:**
QLoRA (Quantized Low-Rank Adaptation) extends LoRA by also loading the frozen base model weights in **4-bit NF4 format** via `bitsandbytes`. This halves the base-weight memory footprint vs float16, bringing total VRAM for a 1.5B model to approximately **6–10 GB** — well within a T4 16GB GPU. The LoRA adapter matrices themselves are still computed in float16 or bfloat16 for numerical stability.

QLoRA does this with three steps:
1. Load frozen base model in 4-bit NF4 quantization — roughly 4× smaller than float16.
2. Add trainable LoRA adapters (A × B) in float16. Only these are updated by the optimizer.
3. During the forward pass, dequantize each 4-bit block to float16 for the computation, then discard the dequantized copy immediately.

**Trade-offs: LoRA vs QLoRA**

| | Standard LoRA | QLoRA |
|---|---|---|
| Base model precision | float16 (~3 GB for 1.5B) | 4-bit NF4 (~0.9 GB for 1.5B) |
| Total VRAM (1.5B) | ~12–20 GB | ~6–10 GB |
| Accuracy vs full-param | Very close (< 0.5 pp typical) | Very close (< 1–2 pp typical) |
| Speed | Faster per step | Slightly slower (dequant overhead ~5–15%) |
| Hardware requirement | CUDA; 16–24 GB sufficient | CUDA required; `bitsandbytes` library; no Apple Silicon MPS support |
| Adapter size | ~20–80 MB | ~20–80 MB (same, adapters not quantized) |
| Reproducibility | High | High if `bitsandbytes` version is pinned |

For this project QLoRA is the correct choice because:
- A T4 16GB (the minimum accessible GPU) fits 1.5B QLoRA with room to spare; the same GPU may be tight with standard LoRA depending on batch size and sequence length.
- The 5–15% slower step speed is acceptable given the small training set (~20–21k rows, 2–3 epochs).
- The small accuracy gap from 4-bit quantization is not meaningful for the B vs E comparison, because both conditions use the same quantization.
- The adapter artifact is the same size as standard LoRA and can be shared in the same way.

The resulting adapter is approximately 20–80 MB regardless of the base model size. For this project the central experiment varies training data (Conditions B vs E), not architecture, so an equivalent and reproducible fine-tuning method across conditions is more important than maximizing absolute performance in any single run.

**LoRA rank selection for this project:**

The rank `r` controls the expressiveness of the adapter. A higher rank trains more parameters and can model more complex task-specific differences, but also increases VRAM usage and overfitting risk on small datasets.

Guidelines:

| Rank | Trainable parameters (approx, 1.5B model) | When appropriate |
|---|---|---|
| r = 4 | ~1M | Very small dataset (<1k), risk of overfitting, minimal VRAM |
| r = 8 | ~2M | Good default for single-domain SFT with 5k–20k examples |
| r = 16 | ~4M | Stronger signal needed, larger dataset, more VRAM available |
| r = 32 | ~8M | Closer to full-parameter behaviour, rarely needed for SFT |

For this study with approximately 20k original seed_train rows (Condition B) and 20k + ~1k synthetic (Condition E), **r = 8 is the recommended starting point**. If validation macro-F1 plateaus early and training loss is still high, try r = 16 in a follow-up run. Do not change rank between Conditions B and E; the adapter rank must be identical for a fair comparison.

Additional LoRA configuration to document for each run:

- Target modules (which linear layers receive adapters; e.g. `q_proj`, `v_proj`, optionally `k_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`)
- `lora_alpha` (scaling; typically 2× rank, so 16 for r = 8)
- `lora_dropout` (typically 0.05–0.1 for regularisation)
- Whether bias parameters are trained

### 9.4 Training approach: synthetic-data distillation versus alternatives

Synthetic-data distillation in this study is not a separate training algorithm. It is supervised fine-tuning (SFT) in which part of the training data is written by a teacher model. The training objective, optimiser, and QLoRA recipe are identical across conditions; only the data source changes. This makes the effect of teacher-generated data measurable in isolation.

**Compared with SFT on original data only.** Plain SFT on the Bitext `seed_train` partition is retained as Condition B, the baseline. It is not rejected; it is the control. The limitation it cannot address is coverage: the curated seed set has limited phrasing diversity and few noisy, multi-intent, out-of-scope, or adversarial requests. Collecting more human-labelled data to fill those gaps is slow and costly. A teacher model can produce targeted examples of exactly those cases (section 8.4) for a one-time API cost. The research question is therefore whether adding such data to SFT (Condition E) improves on plain SFT (Condition B).

**Compared with reinforcement fine-tuning (RLHF, PPO, DPO, GRPO, or grader-based reinforcement fine-tuning).** Reinforcement methods optimise the model against a reward signal rather than imitating target outputs. They are not chosen for this study because:

- The task has clear target outputs (an intent label and a policy-compliant reply), which suits imitation learning directly. Reinforcement methods add most value when good outputs are easy to score but hard to write.
- They require a reward model, a grader, or preference pairs, each of which must itself be built and validated. A flawed reward invites reward hacking, which would confound the comparison.
- Training is less stable and more compute-intensive than SFT, which conflicts with the cost constraints in section 11.4.
- Reinforcement fine-tuning is normally applied after an SFT stage, not instead of it. An SFT baseline is needed first in any case.
- Changing the training algorithm and the data source at the same time would make it impossible to attribute any improvement to the synthetic data.

Preference-based refinement (for example, DPO on pairs ranked by the model judge) is recorded as future work, to be applied on top of the best SFT checkpoint.

## 10. Functional requirements

### FR-1: Data ingestion

The pipeline must download or accept a versioned seed dataset, validate its schema, normalize fields, and generate a data-quality report.

### FR-2: Synthetic generation

The pipeline must generate structured synthetic examples from selected seeds and taxonomy definitions. It must persist model name, prompt version, parameters, token usage, cost estimate, timestamps, and parent seed IDs.

### FR-3: Filtering

The pipeline must apply deterministic and model-based quality checks, preserve rejected examples for analysis, and record rejection reasons.

### FR-4: Dataset versioning

Each training dataset must have a manifest containing its source versions, row counts, class distribution, prompt versions, filters, checksums, and creation date.

### FR-5: Fine-tuning

The training system must support QLoRA/SFT (see section 9.3 for method rationale and rank guidance), deterministic seeding where possible, resumable checkpoints, configurable hyperparameters, and experiment logging. All training examples must be tokenized and chat-template–formatted using the pinned student tokenizer before training; the tokenizer revision, LoRA rank, alpha, dropout, and target modules must be logged alongside every training run.

### FR-6: Evaluation

The evaluation suite must score every experimental condition on the same frozen test sets and produce aggregate, per-intent, per-difficulty, safety, latency, and cost results.

### FR-7: Inference service

The final student model must be accessible through a small API or interactive demo with structured input validation, error handling, and latency measurement.

### FR-8: Reproducibility

A new developer must be able to reproduce data processing, a small generation run, fine-tuning, and evaluation from documented commands and configuration files.

## 11. Experimental design

### 11.1 Required conditions

| ID | Condition | Purpose | Current scope |
|---|---|---|---|
| A | Base student without fine-tuning | Establish zero-shot baseline | Required (evaluation only; no GPU train) |
| B | Student fine-tuned on original curated data | Establish ordinary SFT baseline | Required (1 training run) |
| C | Student fine-tuned on unfiltered synthetic data | Measure raw synthetic-data value | Deferred |
| D | Student fine-tuned on filtered synthetic data | Measure filtering value | Included if a third training run is feasible |
| E | Student fine-tuned on original plus filtered synthetic data | Test primary hypothesis H1 | Required (1 training run) |

Primary comparison for this study: **A vs B vs E** — whether adding approximately 1,000 filtered synthetic examples improves the original-data student. Condition D, if run, additionally informs H2 (filtering) without an unfiltered-synthetic training run.

### 11.2 Recommended ablations (full research design; deferred)

- Synthetic-data volume: 1k, 5k, 10k, and 20k examples.
- Teacher tier: inexpensive versus balanced versus strongest teacher.
- Filtering: deterministic only, model judge only, and combined filtering.
- Data composition: balanced versus natural class distribution.
- Student size: approximately 1.5B versus 3B parameters.
- Difficult examples: included versus excluded.

These ablations are out of scope for this study and should be reported as limitations and future work.

### 11.3 Controls

- Use identical frozen evaluation sets across conditions.
- Hold training steps or observed training tokens constant where appropriate.
- Repeat important experiments with multiple random seeds.
- Record prompt, dependency, model, dataset, and hardware versions.
- Prevent test examples or close paraphrases from entering teacher prompts or training data.

For this study, use **one locked student training recipe** (learning rate, epochs or steps, batch size, LoRA rank) selected on the validation set from Condition B or a small pilot. Hyperparameters must not be retuned per condition. Multiple random seeds are deferred.

**Starting training recipe (to be confirmed on a Condition B pilot, then locked):**

| Setting | Value |
|---|---|
| Learning rate | `2e-4`, cosine schedule, warmup ratio `0.03` |
| Optimizer | `paged_adamw_8bit` |
| Epochs | `2` (maximum `3`); keep the best epoch by validation macro-F1 |
| Per-device batch size | `8` on a T4; `16` on an L4 or A100 |
| Gradient accumulation | `4` on a T4; `2` on an L4 or A100 (effective batch size 32 in both cases) |
| Max sequence length | `512` tokens |
| Precision | `fp16` on a T4 (no bf16 support); `bf16` on an L4 or A100 |
| Gradient checkpointing | Enabled |
| LoRA | `r = 8`, `lora_alpha = 16`, `lora_dropout = 0.05` (see section 9.3) |
| Random seed | `42` |

Rationale:

- **Sequence length.** A Bitext example is roughly 12 tokens of customer message and 150 tokens of reply, plus chat-template overhead, giving about 200–250 tokens. A limit of 512 covers this without wasting memory. Confirm with student-tokenizer length statistics before locking.
- **Run length.** About 20,000 training rows at an effective batch size of 32 is about 625 optimiser steps per epoch, or about 1,250 steps over 2 epochs.
- **Learning rate.** LoRA adapters typically need a higher learning rate than full fine-tuning; `1e-4` to `2e-4` is the usual range. If validation loss is unstable in the pilot, lower it to `1e-4` and apply the same value to every condition.
- **Effective batch size.** Holding the effective batch size at 32 keeps results comparable if Conditions B and E are trained on different GPU types.

**Training-length decision for Conditions B and E:**

Condition E contains about 1,000 more rows than Condition B, so with a fixed number of epochs it receives roughly 5% more optimiser steps. Two options satisfy the control in this section:

1. Fix the number of epochs for both conditions and report the step and token counts of each run.
2. Fix `max_steps` to the same value for both conditions, so Condition B repeats some examples to match Condition E.

Option 1 is preferred for this study because the step difference is small and repeating examples in Condition B would introduce a different confound. The step and token counts of every run must be recorded and reported alongside the results.

**Checkpoint and epoch selection (minimum requirement for this study):**

- Save the final adapter checkpoint at the end of each training run (Conditions B and E). LoRA adapters are approximately 20–80 MB each.
- Record validation loss and validation macro-F1 at the end of every epoch.
- Select the epoch with the best validation macro-F1 as the checkpoint used for frozen held-out and challenge evaluation.
- Saving a checkpoint at every epoch end is recommended so the best epoch can be reloaded without retraining; delete non-best checkpoints after selection to save disk.
- Trained adapters should be pushed to a version-controlled store (e.g. Hugging Face Hub private repo) rather than relying on ephemeral GPU session storage.

### 11.4 Cost-constrained execution plan

Teacher generation uses an **API**. Local development hardware runs ingestion, partitioning, and API orchestration. Student QLoRA requires a CUDA GPU when available; a 16GB unified-memory workstation is not the training target.

| Stage | Volume | Notes |
|---|---|---|
| Prompt pilot | **100–200** raw synthetic examples | Measure schema-valid rate, $/example, and seconds/example; revise prompts |
| Main generation | **approximately 1,000** raw examples (up to **2,000** if measured unit cost permits) | Draw seeds only from `seed_train`; generate about 20–25% extra so filtering can still leave about 800–1,000 accepted rows |
| Filtering | Deterministic checks required; model-based judging if budget permits | Keep rejected rows for analysis |
| Human review | Small stratified sample of the 1k set | Record agreement; a full labelling pass is not required for this study |
| Training runs | **A** (evaluation only) + **B** + **E**; **D** if compute remains | Same hyperparameters; only the data mixture changes |
| Evaluation | Frozen validation, Bitext held-out test, and challenge set | Independent non-Bitext test remains best-effort / future work if no external source exists |

Do **not** generate the 5k / 10k / 20k volume ladder in this pass. Scale only after the 200-example pilot cost is known:

```text
estimated_cost(N) ≈ (pilot_cost / n_pilot) × N
```

## 12. Evaluation plan

### 12.1 Intent metrics

- Accuracy.
- Macro-F1 and weighted-F1.
- Per-intent precision, recall, and F1.
- Confusion matrix.
- Out-of-scope detection AUROC/F1 where applicable.
- Calibration error where confidence scores are available.

### 12.2 Response metrics

- Task correctness.
- Relevance and completeness.
- Policy compliance.
- Hallucination rate.
- Correct clarification or escalation behavior.
- Safety failure rate.
- Human preference or rubric scores.

Lexical-overlap metrics must not be treated as sufficient measures of response quality.

### 12.3 Operational metrics

- Median and p95 latency.
- Input and output tokens.
- Generation, training, and evaluation cost.
- Peak GPU memory.
- Training duration.
- Throughput.
- Model artifact size.

### 12.4 Statistical analysis

- Report sample counts and confidence intervals.
- Use bootstrap intervals or suitable paired tests for primary comparisons.
- Correct or clearly qualify multiple comparisons.
- Include effect sizes, not only p-values.
- Analyze failure categories and representative examples.

### 12.5 Research report plan

The research report should be short and follow this outline:

1. **Introduction.** The research question (section 3) and why small customer-support models need more diverse training data.
2. **Method choice.** Why synthetic-data distillation through SFT was chosen over SFT on original data alone and over reinforcement fine-tuning (summarised from section 9.4).
3. **Data.** Bitext seed set, frozen partitions, challenge-set rationale, teacher prompt version, variation mix, and filtering results (generated, accepted, and rejected counts with reasons).
4. **Training setup.** Student model, QLoRA configuration, the single locked hyperparameter recipe, pinned tokenizer, and best-epoch selection rule.
5. **Results.** Conditions A, B, and E (and D if run) on the held-out test and challenge sets: macro-F1, per-intent results, and response-quality scores, with sample counts.
6. **Cost.** Teacher API cost, GPU hours, and the cost per accepted synthetic example.
7. **Error analysis.** Representative failures, especially on rare, noisy, multi-intent, and out-of-scope inputs.
8. **Limitations and future work.** Bitext is not an independent real-world test set; single random seed; about 1,000 synthetic examples only; deferred ablations; preference-based or reinforcement refinement.

A negative or null result for H1 is reported in the same structure.

## 13. Success criteria

**This study:** successful when Conditions A, B, and E have been evaluated on the frozen held-out and challenge sets, the comparison is reported with sample sizes and limitations, and the pipeline from ingest through evaluation can be reproduced from configuration files. A negative or small H1 result remains a valid research outcome.

**Full research design (deferred):** additionally require C and D, volume ablations, uncertainty estimates on an independent test set that is not teacher-generated, and the targets below.

Initial target values, to be finalized after baseline measurement:

- Scoped: report Condition E vs B honestly; do not require a 3-point macro-F1 gain at ~1k synthetic scale.
- Full design: at least 3 percentage points improvement in macro-F1 over original-data-only SFT, or a clearly justified equivalent improvement in response quality.
- Less than 2% critical safety or policy failures on the challenge set.
- At least 80% schema-valid synthetic generations before filtering (measure on the 200-example pilot first).
- Human-reviewed agreement on a small stratified sample; 90% of all accepted labels is deferred.
- Reproduction of the main evaluation table from a documented command.

## 16. Responsible AI, privacy, and security

- Do not include real personal or confidential customer information.
- Detect and remove generated PII before training or publication.
- Document teacher-provider data-handling settings and retention policy.
- Respect source-dataset and model licences.
- Record synthetic-data provenance in the dataset card.
- Evaluate demographic, language, and tone-related performance disparities.
- Prevent the demo from claiming authority over refunds, payments, legal decisions, or account changes.
- Require escalation for sensitive, unsafe, or unsupported cases.
- Treat LLM-judge scores as fallible measurements and validate them against human review.

## 17. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Teacher generates incorrect labels | Student learns systematic errors | Label checks, independent judge, human sample review |
| Synthetic examples lack diversity | Apparent scale without generalization | Diversity prompts, embedding analysis, coverage reports |
| Train-test leakage | Inflated results | Pre-split data, semantic leakage checks, independent test creation |
| Same model family generates and evaluates | Biased evaluation | Independent evaluator, deterministic metrics, human review |
| Dataset licence is unclear or restrictive | Cannot publish artifacts | Licence audit and publish only permitted derivatives |
| API costs exceed budget | Incomplete experiments | Pilot runs, token caps, batching, caching, tiered teachers |
| Limited GPU availability | Training delays | QLoRA, small models, sampled experiments, checkpointing |
| Student memorizes canned responses | Poor real-world behavior | Challenge set, paraphrase testing, response diversity analysis |
| Results are negative | Perceived project failure | Pre-register hypotheses and present rigorous negative findings |

## 18. Milestones

### Phase 1: Baseline and data audit

- Create repository and reproducible environment.
- Ingest, profile, and document the seed dataset.
- Define task taxonomy and response policy.
- Freeze validation, independent test, and challenge sets.
- Evaluate the base student and original-data SFT baseline.

### Phase 2: Synthetic-data pilot

- Design versioned generation prompts and schemas.
- Generate **100–200** pilot examples via teacher API.
- Measure schema validity, diversity, label consistency, **latency, and $/example**.
- Conduct initial human review of a small sample and revise prompts.

### Phase 3: Generation and filtering

- Generate the **main approximately 1,000** synthetic dataset (up to 2,000 if measured unit cost permits), from `seed_train` only.
- Apply validation, deduplication, quality scoring, and review; keep rejected rows.
- Publish data manifests and quality reports. Do not run 5k/10k/20k in this pass.

### Phase 4: Fine-tuning and experiments

- Train **B** and **E** (**D** if compute remains). Evaluate **A** without training.
- For each run: save a checkpoint at the end of every epoch; record validation loss and macro-F1 per epoch; select the best-epoch checkpoint for held-out evaluation.
- Skip volume and teacher-tier ablations.
- Track hardware, cost, hyperparameters, and the single training-recipe seed.

### Phase 5: Evaluation and analysis

- Run frozen evaluations on held-out and challenge sets.
- Report sample counts and qualitative error analysis; full bootstrap/multi-seed stats are deferred if compute is limited.
- Write the research report, including scope limitations.

### Phase 6: Deployment and publication

- If a trained adapter is available, a small inference demo may be included.
- Publish model and dataset cards where licensing permits.
- Documented repository with configurations sufficient to reproduce the main table.

## 20. Open decisions

- Final teacher model (prefer an inexpensive balanced API for the 1k run unless quality from the pilot is poor).
- Maximum API budget: size the 1k run from the 200-example pilot; do not commit to 20k.
- Whether the main task is intent classification, response generation, or a structured combination of both.
- Independent test-set source and human-review process (Bitext held-out is provisional).
- Final response-policy specification.
- Primary metric: macro-F1 and/or rubric response quality on frozen eval; do not require a 3-point gain at 1k scale.
- Student training hardware: CUDA GPU for Conditions B and E; local development machine for ingest, partition, and API generation only.
- Experiment-tracking and dataset-versioning tools.
- Publication constraints imposed by seed-data and teacher-model licences.

## 21. Definition of done

This study is complete when ingest and frozen partitions exist, a documented 100–200 example generation pilot and an approximately 1,000-example main synthetic set have been filtered, Conditions A, B, and E have been evaluated on the frozen held-out and challenge sets, main results can be reproduced from configuration files, and the research report states what was deferred (Condition C, volume ablations, a non-Bitext independent test, multi-seed statistics). The full research design in sections 11.1–11.2 remains a longer-term target and is not required for completion of this study.
